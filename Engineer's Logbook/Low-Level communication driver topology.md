the level communication drivers are meant to be the link that gets data from the end-point and onto the user's dish (aka the COM Handler). And due to the end-point indifference design choice, the drivers need to be able to handle different communication types, with the most common two being streams and packets. Streams are an unending hail of bytes without any idle-time, like the data being streamed out of a LIDAR sensor. Packets are individual framed groups of bytes with idle-time in-between. I need a driver that can move both, the following topologies were the ones available on the table : 

- Two explicit "stream" and "packet" modes that can be switched between by the user. Pros : very simple to implement, and leaves management up to the end-user. Cons : Two buffers are needed which takes up unnecessary memory, and the driver can be bricked if the user doesn't switch correctly. 
- Treating all data as a "stream" and leaving all parsing to the user. Pros : very very simple to implement. Cons : Parsing byte-arrays in LUA is painfully slow and inefficient.
- A soft hybrid mode where the driver always expects packets, but if a "packet" gets too large, the driver switches to stream mode and streams data cleanly until the stream ends, then it returns to packet mode. Pros : very versatile against end-points that switch their communication architecture during operation. Cons : Implicit mode switching can easily lead to the user trying to read a packet during stream mode, or read a stream in packet mode.

Why the split? Stream mode relies on "double buffering" where we use a circular buffer and move data by reading one half of the buffer while the other is being written to, then reading the new half while the old one is being over-written. This concept is used a lot in streaming large amounts of data like in Audio systems or even in computer graphics. double buffering with hardware DMA buffers in stm32 relies on two interrupts, the half-complete and full-complete which are self-explanatory. However Packet mode, atleast in my case, relies on an Idle-Line interrupt (which is unique to UART) which fires when the driver spends one-byte frame idle. This way instead of relying on frame-delimiters which change wildly from end-point to end-point, I rely on timing to frame the packet. 

With that explanation, we can see that relying on the stream architecture means we lose the temporal factor and have to rely on software to parse packets, but getting the temporal factor means we lose the ability to stream data that is longer than the buffer.

## Old choice
I will choose topology #1, as it is the safest option for a system that is meant to operate continuously, the inefficiency of #2 and over-abstraction of #3 make #1 worth it, and the extra memory issue can be solved by using one buffer for both and resetting it at every switch between modes.

## Currently in use
I ended up choosing topology #2, using idle-line interrupts to packetize the incoming and outgoing data, like in topology #1, seems smart but it puts a timing constraint on the driver, incoming packets must be contiguous with a separation between and outgoing packets must have a separation delay between their transmits, which would necessitate a function that executes actively in a main loop or task for timing, instead of the default reactive nature of the driver. I implemented topology #2 in the latest version of the driver at https://github.com/HamzaHoms/Utils in the buffers.xx files.
